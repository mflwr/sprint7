# Общие требования безопасности

- Разделение сетей (network segmentation)
  Трафик между мобильным приложением, внутренними сервисами PropDevelopment и платформой партнёра должен идти через  выделенные защищённые каналы (VPN или приватное API-VPN) и не пересекаться с остальным корпоративным трафиком

- Шифрование каналов связи
  Все HTTP-запросы должны идти по HTTPS (TLS 1.2+)
  Внутренние RPC/Message-bus при необходимости — по mTLS (mutual TLS)

- Контроль целостности и подлинности
  Все пакеты (JSON-payload) подписываются HMAC-SHA256 с секретным ключом, согласованным заранее
  Ответы партнёра содержат в заголовке X-Signature — HMAC подпись тела

- Периодическая ротация ключей
  Секреты (TLS-сертификаты, HMAC-ключи) обновляются не реже чем раз в 90 дней

- Защита от replay-атак
  Каждое API-сообщение содержит уникальный nonce и таймштамп; партнёр отвергает запросы с устаревшим или повторяющимся
  nonce

- Логирование и мониторинг

Все вызовы к внешнему API заносятся в централизованный SIEM: время, источник, endpoint, результат (успех/ошибка).
Настроены оповещения при аномальной активности (более X неудачных попыток в минуту, неожиданный объём вызовов и т.п.)

# Протоколы аутентификации и авторизации

| № | Тип сервиса               | Аутентификация                        | Авторизация                                 |
|---|---------------------------|---------------------------------------|---------------------------------------------|
| 1 | Интеллектуальный домофон  | OAuth 2.0 Client Credentials Grant:   | RBAC на уровне API-ролей:                   |
|   |                           | — клиент (PropApp) получает JWT-токен | — `gate:open`, `gate:biometric:verify`      |
|   |                           | от внутреннего Authorization Server.  |                                             |
| 2 | Интеллектуальный шлагбаум | OAuth 2.0 Mutual TLS (mTLS) + JWT     | RBAC:                                       |
|   |                           | — клиент идентифицируется по          | — `barrier:open`, `barrier:plate:recognize` |
|   |                           | клиентскому сертификату.              |                                             |

## Описание flows

### Client Credentials Grant

- PropApp запрашивает у своего Authorization Server JWT с claim’ами: sub=propapp, scope=domofon:open domofon:verify.
- При вызове API домофона передаёт в заголовке Authorization: Bearer <token>.

### mTLS + JWT

- PropApp устанавливает TLS-соединение, подтягивая свой клиентский сертификат, доверенный партнёром.
- В рамках TLS handshake партнёр проверяет сертификат, затем приложение включает в запрос JWT, подписанный тем же сертификатом.

## Организация взаимодействия систем

### Прокси-шлюз (API Gateway)

- Все вызовы от мобильного приложения пропускаются через API Gateway PropDevelopment:
- Проверка токена (JWT в OAuth 2.0 flow) или клиентского сертификата (mTLS).
- Применение rate limiting, WAF-правил.
- Аудит и трассировка запросов (distributed tracing).

### Асинхронная обработка событий

События распознавания (лицо/номер) и открытия дверей/шлагбаума публикуются в Kafka/AMQP:

- Producer: платформа партнёра шлёт событие door.opened или barrier.opened
- Consumer: сервис PropDevelopment сохраняет факт в журнале безопасности, уведомляет клиента через push-уведомление

### Fallback-механизмы

В случае недоступности внешнего API:

- Предусмотреть аварийное открытие по пину/паролю

### Контракты API и документация

- RESTful JSON-контракты с OpenAPI 3.0 спецификацией, согласованной между сторонами
- Обязательно версии API (v1, v2…) и backward-compatibility правила

### Управление SLA и SLO

- SLA для отклика API ≤ 300 ms
- SLO по доступности ≥ 99.9 %
